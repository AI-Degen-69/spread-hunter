במילים פשוטות: מה השתנה?

כשהבוט מסיים ריצת סימולציה או מסחר ומדווח שהרווחנו 1.00$+, עד עכשיו ראינו רק שורה אחת כללית: "רווח כולל: 1.01$+". המספר הזה לבדו עלול היה להטעות, כי הוא לא גילה מאיפה הכסף באמת הגיע.

הניתוח החדש מפרק את ה-PnL לשלושה מקורות מדויקים: כמה מהרווח הגיע מזוגות נקיים ששני צדדיהם נתפסו כ-Maker (עמלת אפס ומקסימום רווח), כמה הגיע מזוגות שהושלמו באגרסיביות כ-Taker כדי למנוע הישארות עם רגל בודדת, וכמה הגיע מניהול סיכונים של יציאת חירום (Rescue Exit). כך אפשר לראות ברגע האם הרווחיות מגיעה מאסטרטגיית הליבה או מאירועי חירום.

לפני מול אחרי

לפני: מספר PnL בודד ושטוח

  • הדוחות והדשבורד הציגו רק מספר Realized PnL כולל.
  • כדי לדעת כמה הגיע מ-maker, taker או rescue היה צורך לבצע ניתוח ידני ב-SQL/פייתון.
  • אי אפשר היה לדעת האם שורת הרווח נובעת ממזל ביציאות חירום או ממילוי זוגות מוצלח של הבוט.
  • דוח האימות הסטטיסטי היה חסר את הפירוט הקריטי לקבלת החלטות.

אחרי: פילוח תלת-ראשי מדויק

  • חישוב אוטומטי של PnL ואחוזי תרומה לפי 3 מסלולים מוגדרים היטב:
    maker_merged זוג מלא שנקנה פסיבית כ-Maker.
    taker_completed זוג שרגל אחת שלו הושלמה כ-Taker.
    single_buy_exit פוזיציה שנחתכה ביציאת חירום/הצלה.
  • משולב במלואו ב-KPI Core (`core_brain/kpi.py`).
  • מוצג ישירות בדוח האימות הסטטיסטי (`report.md` ו-`report.json`).
  • מוצג ב-UI של הדשבורד בכרטיס ה-Run Profitability.

שלושת מסלולי המילוי שהוגדרו

01 · MAKER MERGED

maker_merged

שתי רגלי הזוג (UP + DOWN) נתפסו בהזמנות Maker פסיביות בספר הפקודות ומוזגו ל-USDC ברווח מרבי ללא עמלות לקיחה.

02 · TAKER COMPLETED

taker_completed

רגל אחת נתפסה אך השנייה לא; הבוט השלים את הרגל החסרה כ-Taker כדי להבטיח זוג שלם ולמזג ל-USDC בבטחה.

03 · RESCUE EXIT

single_buy_exit

רגל בודדת שנשארה יתומה ולא הצליחה להשלים זוג נחתכה בשוק חזרה ל-USDC כדי להגן על הקרן (חילוץ פוזיציה).

מדריך בדיקה ידנית (Touch & See)

אין צורך להריץ טסטים (הסוכן ו-CI עשו זאת). המדריך להלן מאפשר לראות את הנתונים בעיניים על מערכת עובדת:

1. הפקת פלט KPI בטרמינל ובדיקת השיוך

הרץ את מודול ה-KPI. הפלט יציג את הבלוק החדש pnl_by_fill_path עם חלוקה ל-3 המסלולים:

python -c "from core_brain import kpi; rep = kpi.report(); import json; print(json.dumps(rep.get('pnl_by_fill_path', {}), indent=2))"
מה אמורים לראות: אובייקט JSON המכיל את המפתחות maker_merged, taker_completed, single_buy_exit, total ואת המילון pct.

2. הפקת דוח אימות סטטיסטי ובדיקת החלק "Rescue & failure modes"

הרץ את הפקת הדוחות כדי לראות את הייצוג ב-Markdown וב-JSON:

python -m statistical_validation_run.artifacts
מה אמורים לראות: הקובץ reports/report.md עודכן וכולל תחת ## Rescue & failure modes שורות מפורטות של Maker-merged PnL, Taker-completed PnL, ו-Single-buy exit PnL עם אחוזי הפיצול.

3. פתיחת הדשבורד ובדיקת תצוגת ה-Profitability

הדשבורד שלך כבר פעיל ברקע בכתובת http://127.0.0.1:8799. פתח אותו בדפדפן וצפה בכרטיס הרווחיות:

Start-Process "http://127.0.0.1:8799"
מה אמורים לראות: בכרטיס ה-Run Profitability / Analytics מופיע כעת פירוט השיוך בפורמט: maker $X (A%) · taker $Y (B%) · rescue $Z (C%) ללא שבירת העיצוב הקיים.

קבצים שהשתתפו בשינוי

קובץ תפקיד והשפעה
core_brain/kpi.py מימוש הפונקציות find_taker_completed_pairs ו-pnl_by_fill_path, וחיבורן ל-report().
statistical_validation_run/artifacts.py חילוץ נתוני הפיצול לתוך report.json ועיצוב שורות הפיצול ב-Markdown תחת Failure Modes.
dashboard/static/app.js הצגת פירוט הפיצול (Maker / Taker / Rescue) בשורת הפירוט של כרטיס הרווחיות בריצה.
tests/test_pnl_by_fill_path.py בדיקות ייעודיות שאימתו את הפיצול המדויק 25% maker / 35% taker / 41% rescue ומקרי קצה.
SPEC.md / CONSTRAINTS.md / tasks/ נעילת המפרט, הסכמים מול סקירת קוד והגדרת תחנות העבודה.
